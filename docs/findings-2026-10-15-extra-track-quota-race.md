# Находка 2026-10-15: квота «своих дорожек» не держала лимит при одновременных загрузках

Дата: 2026-10-15. Автономный прогон по мандату из `CLAUDE.md`. Вчерашние
коммиты (`5d4a859`, `3d1254d`, `a794f8a`) принесли запись голоса, FX,
сведение одной кнопкой, нейросеть для записанной дорожки и ссылку
«послушать» — большой, ещё не проверенный прошлыми раундами объём кода.
Начал с него.

## Исправлено: `POST /api/studio/{job_id}/extra` — гонка на лимите `EXTRAS_PER_TRACK`

`web/app.py:api_studio_extra` (своя дорожка мультитрека — запись с
репетиции, подложка, любой загруженный файл) проверяла лимит в 16 дорожек
на трек по снимку `job`, снятому **до** перекодировки ffmpeg — самой
медленной части запроса (до 300 с таймаута). Итоговая запись в базу шла
под замком (`studio_runner._analysis_lock`) с повторным чтением `fresh =
storage.job(job_id)`, но лимит по этому свежему чтению заново не
проверялся — дорожка дописывалась безусловно.

Сценарий: трек уже у квоты (15 из 16 дорожек). Два запроса на загрузку
приходят почти одновременно (например, с двух открытых вкладок, или
автозагрузка только что записанного дубля совпала с ручной загрузкой
файла). Оба читают `job` с 15 дорожками, оба проходят проверку `15 >= 16
→ false`, оба конвертируют файл и оба дописывают запись — на выходе 17
дорожек при заявленном пределе 16. При большем числе параллельных запросов
лимит не держит вовсе: сколько придёт одновременно — столько и допишется
сверх квоты, без explicit верхней границы.

Деньгами это не рискует (своя дорожка — бесплатная функция, лимит нужен
только для диска: партии трека и так занимают место, см.
`deploy/README.md` про уборку по `nasluh-cleanup`), но это тот же класс
TOCTOU-гонки, что чинился раньше в `web/jobs.py`/`web/storage.py` для
денежных путей (10-07, 10-10, 10-11) — здесь просто его нашёл свежий код,
а не платёжный.

Фикс: вторая, авторитетная проверка лимита — под тем же замком, по
свежим данным, прямо перед записью; при превышении — файл, уже
созданный перекодировкой, подчищается, прежде чем вернуть 400. Первая
(старая) проверка оставлена как есть — она отсекает большинство лишних
загрузок ещё до дорогой перекодировки, экономя CPU.

Регрессионный тест (`tests/test_studio.py:
test_extra_track_quota_holds_even_when_a_parallel_upload_fills_it_first`)
подменяет `storage.job` так, что второе (под замком) чтение видит квоту
уже заполненной «параллельной» загрузкой — проверен на коде ДО фикса
(тест падает, лимит не держит и файл остаётся на диске) и ПОСЛЕ (тест
проходит).

## Проверено без находок

- **Ссылка «послушать» (`/listen/{token}`, `web/app.py`)**: владение
  (только свой трек), запрет для каверов (`rights.kind == "cover"`,
  п. 6.3 оферты — авторское право), отзыв доступа при удалении трека или
  смене прав — всё проверяется заново на каждое обращение через
  `_shared()`, не кэшируется. Уже покрыто тестом
  `test_share_link_plays_without_login` (там же, в коммите `3d1254d`).
- **`web/voicefx.py`** (шумодав DeepFilterNet, подтяжка нот pYIN+PSOLA):
  все вызовы `subprocess` — списком аргументов, не через shell; значение
  `key` (из формы, пользовательский ввод) никуда не попадает в команду,
  только в `scale_of()` через `re.match` — инъекция исключена.
  Эта обработка бесплатна для пользователя (CPU-фича, не через кредиты) —
  соответствует коммиту: намеренно, не упущенное списание.
- **`web/static/mixbus.py` (сведение, BS.1770, ограничитель)**: нашёл
  единственную неточность — в K-взвешивающем фильтре (`kCoefs`, ВЧ-срез
  38 Гц) коэффициенты `b` не делятся на `a0`, хотя `a` делятся (как в
  соседнем шелфе). На 44100 Гц это даёт `a0 ≈ 1.0054`, то есть ошибку
  порядка 0.05 дБ в измерении громкости — не стал трогать: это не баг на
  слух и не воспроизводимый тестом сценарий, а числовая погрешность
  на три порядка меньше, чем шаг громкости между стилями сведения (1–3
  дБ, `web/static/mixbus.js: STYLES`).
- **Выравнивание записи голоса по времени** (`web/static/mix.js:
  stopRecording`, компенсация задержки вывод+ввод): формула проверена
  построчно, логически согласована с точкой отсчёта воспроизведения
  (`startTime`/`startPos`) и с режимом экспорта (`mixdown`, сдвиг
  `lead`). Понять, действительно ли дубль ложится в такт на реальном
  железе (разные браузеры и аудиоинтерфейсы дают разную задержку) —
  нужно живое прослушивание, не статический анализ кода; соответствует
  уже отмеченному в `CLAUDE.md` ограничению на то, что текстовый агент
  может проверить сам.
