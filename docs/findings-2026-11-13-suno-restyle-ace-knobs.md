## Находка: ползунки ACE-Step видны (и бесполезны) при переделке на Suno

`web/static/studio.js::showMode()`:

```js
const mureka = info && info.restyleEngine === 'mureka' && !yue2;
...
$('strengthBox').hidden = !(mode === 'restyle' && !mureka && !yue2);
```

`strengthBox` -- блок с двумя ползунками, «сила исходника»
(`audioKnob` → `audio_influence`) и «удержание мелодии» (`melodyKnob` →
`melody`). Эти параметры имеют смысл только для ACE-Step/RunPod: они идут
в `studio.runpod_restyle_recipe()`, которая в `web/app.py::api_studio_start`
подмешивается в задание **только если** `mode == "restyle" and engine ==
"runpod"` (строки 2322-2323). Когда переделку ведёт Suno (`engine ==
"suno"`) или YuE2, бэкенд эти два поля из формы тихо игнорирует -- но
условие показа блока проверяло только «не Mureka и не YuE2», то есть
молчаливо считало, что всё остальное -- обязательно RunPod. На новом
сервере без ключа Mureka это не так: `studio.suno_public()` держит Suno
главным движком переделки собственной записи (решение владельца 29.10,
закреплено код-ревью сегодняшних коммитов 65e7730/0a1c9c2), и `restyleEngine()`
при этом по-прежнему возвращает `"runpod"` (это просто дефолт функции при
отсутствующем ключе Mureka, а не признак того, что задача пойдёт на
RunPod) -- `mureka` и `yue2` оба `false`, блок показывается.

Пользователь видит два ползунка, двигает их, думая, что управляет
переделкой -- а они ни на что не влияют: бэкенд их для Suno не читает
вовсе. Не денежный баг (списание и генерация идут правильно), но
доверие к интерфейсу подрывает ровно так же, как любой «мёртвый»
контрол -- особенно заметно сразу под настоящими, рабочими настройками
Suno (`hitOpts`: «без чего», смелость, продолжение записи), которые
показываются в этот же момент.

## Фикс

Та же переменная `hit` (результат `hitOn()`), которая уже используется
чуть выше в `showMode()` для `hitOpts`/`contBox`, добавлена в условие
`strengthBox`:

```js
$('strengthBox').hidden = !(mode === 'restyle' && !mureka && !yue2 && !hit);
```

Тест (живой Chromium, `tests/test_studio_browser.py`, новый файл по
образцу `test_mixer_browser.py`): поднимает настоящий uvicorn с
`RUNPOD_API_KEY` (нужен для `studio.available()`), без `MUREKA_API_KEY`,
`NASLUX_YUE2=0`, `GENAPI_API_KEY` -- точная копия сценария «новый сервер
без Mureka» из `test_create_from_scratch_works_on_genapi_alone`
(`tests/test_studio.py`). Заходит на `/studio`, переключает режим на
«Переделать», ждёт появления `hitOpts` (Suno — активный движок) и
проверяет HTML-атрибут `hidden` у `strengthBox` напрямую (а не
видимость на экране: `hitOpts`/`strengthBox` живут внутри сворачиваемых
«Тонких настроек», это отдельный CSS-переключатель, не связанный с
логикой `showMode()`, которую проверяет тест). Проверено, что тест
красный на коде до фикса (`hidden` не выставлен) и зелёный после.

Полный `pytest` после фикса: 482 passed (было 481 + 1 новый), 0 skipped,
без регрессий.

## Что не трогал и почему

- Остальные места с проверкой `info.restyleEngine === 'mureka'` в
  `studio.js` (строки ~198, 208-210, 522-525, 1273, 2111, 2183) --
  прочитаны все по очереди: это настоящие Mureka-only функции без
  аналога у Suno/YuE2 (клонированный голос Mureka, «Как в образце»,
  «Глубокое разделение + MIDI», «Слушаем трек» через `song/describe`) --
  там `=== 'mureka'` корректен, добавлять `!hit` не нужно, это не тот же
  баг.
- Качество распознавания аккордов -- без изменений: гипотеза
  HPSS/BS-RoFormer всё ещё ждёт GPU (не провизионить платную
  инфраструктуру -- пункт мандата), численная проверка на GuitarSet уже
  сделана (22.10, см. `docs/findings-chord-quality.md`) и не изменила
  результат; новых проверяемых идей по качеству распознавания на этот
  прогон не нашлось -- не придумываю правку без конкретного случая.
- `web/voice.py` и `/voice` (проба владельца, клонирование голоса через
  GenAPI) -- новый код, появился 8-9.11, но целевого бага в нём за это
  время найти не успел: нашедшийся выше баг оказался быстрее проверить
  и исправить end-to-end (с красным/зелёным тестом), чем начинать
  вторую, более глубокую ревизию в рамках одного прогона.
- Конкурентный анализ (`docs/competitors.md`) -- обновлялся позапрошлым
  прогоном (11.11), задание просит сверяться не каждый раз; в этот
  прогон не трогал.
