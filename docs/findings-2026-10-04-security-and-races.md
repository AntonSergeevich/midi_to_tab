## 1. OAuth привязывает по email без подтверждения (угон аккаунта) + фарм приветственных кредитов

`web/app.py`: регистрация по паролю не проверяет email, а колбэк OAuth
(Яндекс/VK) находит существующий аккаунт по `user_by_email(email)` и
привязывает к нему новый вход. Сценарий: злоумышленник регистрируется на
чужой `victim@yandex.ru` со своим паролем; когда жертва позже входит через
Яндекс ID с тем же email, колбэк привязывает её вход к аккаунту, пароль от
которого знает злоумышленник, -- жертва платит в аккаунт, доступный чужому
человеку. Побочный эффект того же пробела: `WELCOME_CREDITS` (20 кредитов
Студии) выдаются на каждый новый анонимный id + придуманный email без
проверки -- неограниченный фарм пробных кредитов (реальные деньги,
API-вызовы к Mureka).

Почему не чиним здесь: это не баг в духе "забыли проверить файл", а
решение о том, КАК должна работать привязка аккаунта -- отправлять
письмо-подтверждение, require пароль перед привязкой чужого email,
полностью менять поток входа через OAuth -- то есть продуктовое решение,
а не code-level правка, которую можно безопасно запушить в прод без
ревью. Чинить вслепую на автодеплое рискованно: можно сломать вход
существующим пользователям.

Предполагаемое направление: не привязывать OAuth-вход к существующему
аккаунту автоматически по email -- только создавать новый аккаунт на
этот email либо требовать ввода пароля существующего аккаунта перед
привязкой. `WELCOME_CREDITS` давать только после подтверждения почты
(ссылка на email, уже есть инфраструктура писем -- `web/mailer.py`,
`web/support.py`).

## 2. `_charge_song_once`: окно гонки между захватом и подтверждением оплаты -- ИСПРАВЛЕНО (2026-10-05)

`web/app.py:_charge_song_once`. `claim_job_charge` атомарно ставит
`job.counted=1`, и только ПОСЛЕ этого проверяется `billing.check_access`
и списываются деньги; если которая-то из этих двух проверок не проходит,
`counted` откатывается обратно в 0 (402 вызывающему). В узком окне между
"уже counted=1" и возможным откатом обратно в 0 другой параллельный запрос
к другой партии/табам того же трека видит `claim_job_charge` неудачным
(false, трек уже "в процессе счёта") и трактует это как "уже оплачено
раньше" -- проходит дальше БЕСПЛАТНО. Если первый запрос затем всё-таки
откатывается (нет денег), второй уже успел получить платный результат, не
заплатив.

Фикс: `_charge_song_once` целиком (застолбить -> проверить доступ ->
списать -> при неудаче откатить) оборачивается в один `threading.Lock`
на весь процесс (`web/app.py:_charge_lock`). Сервис и так работает одним
процессом (`--workers 1`, намеренное решение из `deploy/README.md`) --
значит, обычный лок полностью закрывает это окно: второй запрос ждёт,
пока первый не доведёт дело до конца, и видит только непротиворечивое
состояние `counted`, без изменения форм API storage/billing и без
дополнительных вызывающих мест. Регрессия воспроизведена настоящими
потоками с управляемой паузой внутри `billing.check_access`
(`tests/test_web.py::test_charge_song_once_survives_a_true_concurrent_race`)
-- без лока тест ловит гонку (второй поток проезжает мимо лока, пока
первый ещё не решил исход), с локом оба потока корректно получают 402,
если денег ни у кого нет.

## 3. Восстановление после рестарта делает рефанд, а не доигрывает задание

Сегодня добавлено `JobRunner.recover_interrupted()` (web/jobs.py,
вызывается в `lifespan` web/app.py): после `systemctl restart nasluh`
(каждый автодеплой) зависшие "queued"/"running" задания закрываются --
деньги возвращаются, трек можно запустить заново. Это закрывает дыру
"деньги списаны, трек навечно завис", но хуже по UX, чем настоящее
доигрывание: пользователю нужно нажать кнопку ещё раз.

Настоящее доигрывание возможно для `_separate_later`/`_lyrics`/`_tabs` --
им хватает `job_id` (источник уже лежит в `job.result.paths`), но для
`_analyze` нужен путь к загруженному файлу, который нигде не
сохраняется, кроме как явным параметром при самом первом запуске; его
придётся либо писать в `job.settings`, либо восстанавливать по
`uploads/<job_id>/*` (там ровно один файл на задание). Стоит отдельного
захода с тестами: если автодеплой попадёт на файл ровно в процессе
записи/удаления, легко получить другую гонку.
