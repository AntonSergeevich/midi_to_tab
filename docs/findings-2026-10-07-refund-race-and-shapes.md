# Находки 2026-10-07

Два багорезюме двух параллельных ревью кода (web/app.py, web/billing.py,
web/jobs.py, web/storage.py в одном заходе; midi2tab/arrange.py,
shapes.py, timing.py, beatgrid.py, cleanup.py, convert.py, gp5out.py,
asciiout.py, web/oauth.py, web/mailer.py, web/support.py, web/seo.py в
другом). Два найденных бага исправлены в этом же прогоне, два -- записаны
ниже с причиной, почему не трогаем.

## 1. Двойной возврат денег при удалении трека -- ИСПРАВЛЕНО

`web/app.py:api_delete_job` и все точки возврата в `web/jobs.py`
(неудача разбора/разделения/табов/текста, `recover_interrupted` после
перезапуска) читали `job.charged_kind` и решали, возвращать ли деньги,
по снимку -- без атомарной отметки. `JobRunner` крутит свой пул потоков
в одном процессе с пулом синхронных обработчиков Starlette (которые
обслуживают DELETE), так что это настоящая гонка потоков, а не
последовательные вызовы: два почти одновременных DELETE на один и тот же
ещё не отработавший платёж (два клика, или удаление ровно в момент,
когда сам разбор падает) оба видели charged_kind непустым и оба вызывали
`billing.refund` -- кредит или рубль возвращались дважды за одно
списание.

Фикс: `storage.claim_job_refund(job_id, charged_kind)` -- атомарный
`UPDATE jobs SET charged_kind = NULL WHERE id = ? AND charged_kind = ?`,
тот же приём, что уже был в `claim_job_charge` для противоположной
стороны (списания). Каждая из семи точек возврата теперь вызывает
`billing.refund` только если успела снять отметку сама. Регрессия:
`tests/test_web.py::test_deleting_a_job_twice_at_once_refunds_only_once`
-- настоящая гонка потоков (как и существующий
`test_charge_song_once_survives_a_true_concurrent_race`), не
последовательные вызовы.

## 2. Неиграбельные аппликатуры с баррэ -- ИСПРАВЛЕНО

`midi2tab/shapes.py:_best_in_position`: `return shape if shape.fingers
<= MAX_FINGERS or barre else None`. Условие `or barre` пропускало ЛЮБОЕ
число пальцев, стоило лишь обнаружиться баррэ -- проверка на MAX_FINGERS
для баррэ-аппликатур не работала вовсе. В стандартном строе (EADGBE)
единственной найденной аппликатурой для A6 была (5, 4, 4, 6, 5, 5) --
баррэ на пятом ладу плюс три прижатых сверху пальца плюс сам баррэ,
итого 5 пальцев (`Shape.fingers` уже считает баррэ одним пальцем); для
B9 -- (7, 6, 7, 6, 7, 7), тоже 5. Обе руке не взять, а сервис рисовал их
как единственный вариант.

Существующий тест (`test_shapes_never_need_more_than_four_fingers_
without_a_barre`) проверял ровно то же условие, что в продакшен-коде
(`shape.barre or shape.fingers <= MAX_FINGERS`) -- тавтология, которая
никогда не могла поймать эту ошибку.

Фикс: убрали исключение `or barre` -- `MAX_FINGERS` уже учитывает баррэ
как один палец, отдельная поправка не нужна. Тесты: старый тест
переименован и исправлен (`test_shapes_never_need_more_than_four_
fingers`, без тавтологии), плюс новый
`test_barre_shapes_never_need_more_than_four_fingers_either` на
конкретный A6/B9 из находки.

## 3. `deploy/cleanup.py`: уборка по времени изменения ПАПКИ, не по чтению -- не трогаем

`sweep()`/`sweep_stems()` решают удаление по `entry.stat().st_mtime` --
а mtime папки меняется только при добавлении/удалении файлов внутри,
не при чтении. Если загрузка старше `KEEP_UPLOADS_DAYS` (по умолчанию
14 дней) ещё не тронута с момента создания, а пользователь в этот же
момент запускает повторное разделение на партии по старому треку
(`_separate_later` читает `job.result.paths.source`), суточный таймер
уборки (`nasluh-cleanup.timer`) может удалить файл, который воркер
читает конкурентно -- `shutil.rmtree` против открытого файлового
дескриптора.

Почему не чиним сейчас: окно гонки -- доли секунды (между проверкой
`os.path.isfile` в `_separate_later` и собственно чтением файла), а
совпасть должны ОБА редких события: трек старше двух недель и запрос
именно в момент суточного срабатывания таймера. Частичная защита уже
есть (`_separate_later` проверяет `isfile` и отвечает понятной ошибкой,
а не падает молча, если файла нет вовсе) -- остаётся только самое узкое
окно между проверкой и чтением. Настоящий фикс (файловый лок или lease
на время чтения) добавляет реальную сложность ради события, которое
может не случиться никогда при полутора сотнях треков в месяц. Стоит
отдельного захода, если когда-нибудь действительно встретится в логах.

## 4. `web/support.py`: срок по 152-ФЗ считается календарными днями, а не рабочими -- не трогаем

Тема `data` (запрос персональных данных) отмечена `"ответ в течение 10
рабочих дней"`, а `urgency()` считает `deadline_days(topic) * 86400`
календарных секунд -- индикатор "просрочено" в админке для этой темы
загорается на несколько дней РАНЬШЕ настоящего срока по закону (не
позже, что было бы хуже).

Почему не чиним сейчас: ошибка консервативна (торопит ответить раньше,
а не позже дедлайна) и касается только внутреннего индикатора в
админке, не денег и не внешнего поведения сервиса. Правильный фикс
(календарь рабочих дней с российскими праздниками) -- отдельная, не
тривиальная задача ради точности indicator'а, который и так на стороне
осторожности. Не стоит сложности сейчас.
