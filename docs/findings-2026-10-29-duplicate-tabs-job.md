# Находка 2026-10-29: повторный запрос табов для той же партии запускал вторую транскрипцию

Дата: 2026-10-29. Автономный прогон по мандату из CLAUDE.md. Два прохода
(`web/billing.py`/`jobs.py`/`storage.py`/`voicefx.py`/`support.py`/`oauth.py`
и отдельно весь `web/app.py`) не нашли новой денежной гонки -- код атомарных
списаний (`claim_job_charge`, `claim_job_run`, `claim_job_refund`) оказался
таким же строгим, как и в прошлых находках. Эта находка -- из второго
прохода, по месту, которое раньше не разбиралось отдельно.

## Симптом

`POST /api/job/{id}/tabs/{stem_key}` (`web/app.py:api_make_tabs`) при каждом
вызове безусловно создавало новое дочернее задание (`storage.create_job`)
и запускало Basic Pitch (`runner.submit_tabs`) -- в отличие от соседнего
`/separate` (`api_separate_later`), у которого есть явная проверка "уже
разделено" и атомарный захват `claim_job_run` перед запуском.

Кнопка «Создать MIDI и табы» (`web/static/player.js:buildParts`) блокируется
(`button.disabled = true`) только в ТОЙ вкладке, что её нажала, и никогда не
проверяет уже идущие задания: `GET /api/job/{id}` отдаёт дочерние задания в
поле `made`, но `buildMade()` (player.js:190) показывает в нём только
готовые (`status === 'done'`) -- `queued`/`running` там не видны вовсе, а
`buildParts()` вообще не смотрит на `made` при решении, рисовать кнопку
или нет.

Конкретный сценарий: человек нажимает «Создать MIDI и табы» для партии
гитары, затем, не дождавшись (перезагрузка страницы, вторая открытая
вкладка, повтор запроса из-за таймаута мобильной сети), видит ту же чистую
кнопку и нажимает снова -- второй запрос создаёт ВТОРОЕ дочернее задание
и запускает ВТОРОЙ разбор Basic Pitch той же самой партии параллельно
первому.

## Почему это important: один процесс, 3 ГБ памяти

`deploy/README.md`: сервис -- один процесс (`--workers 1`), разбор идёт в
пуле потоков внутри него, `MemoryMax=3G` в systemd-юните. Два параллельных
разбора одной и той же партии не ускоряют результат (второй не отменяет
первый), а просто отбирают память и процессорное время у ЧУЖИХ заданий,
стоящих в очереди у того же сервиса -- то есть это не только зря
потраченная работа, а потенциальный повод для медленных ответов или OOM
другим пользователям в момент пика. Денег это не касается --
`_charge_song_once` списывает один раз независимо от числа дочерних
заданий (его собственная атомарная отметка `counted` это гарантирует,
проверено тестом `test_two_stem_tabs_clicked_at_once_charge_only_once`,
который специально проверяет ДВЕ РАЗНЫЕ партии, а не ту же самую дважды).

## Фикс

Перед созданием нового дочернего задания `api_make_tabs` теперь смотрит на
существующие дочерние задания того же трека (`storage.child_jobs`, уже
использовался для поля `made` -- отдельного запроса не потребовалось) и,
если для этой же партии уже есть НЕзавершившееся ошибкой задание
(`status != "error"`, то есть queued/running/done), возвращает его `jobId`
вместо нового:

```python
for child in storage.child_jobs(job_id):
    if (child.settings or {}).get("stem") == stem_key and child.status != "error":
        return {"jobId": child.id}
```

Ответ остаётся тем же `{"jobId": ...}`, так что фронтенд (`watchTabs`) не
нуждается в правке: если задание уже `done`, первый же опрос статуса сразу
покажет готовый результат; если оно ещё идёт -- просто продолжит следить
за уже существующим заданием. Неудачную попытку (`status == "error"`) не
переиспользуем специально: это обычный повтор «попробовать снова», и его
отличает собственный тест.

## Тест

`tests/test_web.py::test_tabs_clicked_twice_for_the_same_stem_reuses_the_job`
-- два клика по той же партии создают ровно одно дочернее задание и зовут
`runner.submit_tabs` ровно один раз; списание тоже одно (баланс уменьшается
на `PRICE_SINGLE_RUB` только раз). Проверено, что тест ловит именно
починенный симптом: временный `git stash` только `web/app.py` -- падает
(создаются два дочерних задания с разными id), откат не коммитился.

`tests/test_web.py::test_tabs_retried_after_a_failure_starts_a_fresh_job`
-- дополнение: если первая попытка упала (`status="error"`), повтор должен
создать НОВОЕ задание, а не вернуть сломанное старое.

Полный прогон: 436 тестов (было 434) + 2 пропущенных, зелёный.

## Что проверял, но не стал трогать

- Два отдельных глубоких прохода (поручены агентам-подпроцессам) по
  `web/billing.py`, `web/jobs.py`, `web/storage.py`, `web/voicefx.py`,
  `web/support.py`, `web/oauth.py`, `web/releases.py`, `web/benchmark.py`,
  `web/auth.py` и по всему `web/app.py` не нашли новой денежной гонки или
  уязвимости -- весь денежный код уже защищён атомарными захватами с
  комментариями, явно называющими гонку, которую они закрывают (включая
  ссылки на конкретные прошлые находки). Это ожидаемо диминишинг-ретурнз:
  после 24+ находок подряд по этим файлам естественно, что он становится
  всё более устойчивым.
- `midi2tab/cleanup.py` (группировка `max_polyphony` по `start`, не по
  бегущему последнему кадру) структурно похоже на починенный 28.10 баг
  `beatnet._peaks()`, но это намеренное отличие: `cleanup.py` моделирует
  свою группировку по образцу `arrange.group_chords` (тоже от `start`) --
  для "нот в пределах окна истинной атаки" это правильная модель, в
  отличие от склейки долей, которой нужна именно неограниченная смежность
  соседних кадров. Не бага.
- `_merge_short` в `audiochords.py` (слияние коротких аккордов с соседом
  по большей уверенности) теоретически может взять имя короткого,
  переоценённого по уверенности сегмента вместо длинного правильного --
  но это ровно то же явление калибровки уверенности на коротких атаках,
  что уже описано в `findings-chord-quality.md` (HPSS, confidence=1.0 на
  одном такте) и требует размеченных данных для проверки, которых нет.
  Сам `_merge_short` работает ровно так, как говорит его docstring --
  это не баг в реализации, а открытый вопрос калибровки модели.
- Конкурентный анализ не обновлял -- последняя сверка 26.10, три дня
  назад; по мандату («не каждый раз», сверка идёт еженедельно) разумно
  пропустить этот прогон.
