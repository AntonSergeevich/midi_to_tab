## Починено: `beatgrid.retime()` падал на повторяющихся соседних долях

**Симптом.** `midi2tab/beatgrid.py:58` считает шаг сетки до первой и
после последней доли: `first = b[1] - b[0]`, `last = b[-1] - b[-2]`. Если
первые (или последние) две доли в списке `beats` численно совпадают,
`first`/`last` -- 0, и `np.arange(x, y, 0)` на строках 61-62 либо делит на
ноль (RuntimeWarning), либо падает `ValueError: Maximum allowed size
exceeded` (воспроизведено на реальной функции без моков:
`beatgrid.retime(midi_bytes, beats=[1.0, 1.0, 2.0, 3.0])`).

**Почему не ловилось раньше.** `beatnet.steady()` уже отбрасывает доли
ближе 0.75×медианного шага друг к другу, а резервный `librosa.beat_track`
отдаёт строго растущие индексы кадров -- из текущего конвейера
распознавания такой список долей не приходит. Единственный путь на
прод -- вызов `web/studio.py::_align_midi` (строка 2474), который уже
оборачивает `retime()` в широкий `except Exception` и просто пропускает
выравнивание по сетке для этого файла при любой ошибке -- то есть в бою
это не крашит job и не влияет на оплату, только тихо оставляет MIDI
невыровненным. Из-за этого 30 прогонов, искавших крэши/деньги на
обычных входах, баг не задели -- он живёт в защите от нестандартного
входного `beats`, а не на типичном пути.

**Фикс.** `first, last = max(b[1] - b[0], 1e-3), max(b[-1] - b[-2], 1e-3)`
вместо прямой разности -- `np.arange` больше не получает нулевой шаг;
поведение на нормальных (строго растущих) `beats` не меняется, потому что
`max(positive, 1e-3)` равен исходному значению для любого реального шага
между долями (доли не бывают ближе 1 мс друг к другу).

У `retime()` есть буквальная копия в `yue2/ss_run.py` (свой образ/venv,
без пакета `midi2tab`) -- `tests/test_beatnet.py
::test_beatgrid_retime_matches_the_yue2_copy` сверяет тела функций через
AST и упала бы, если бы я поправил только один файл. Применил то же
исправление (одинаковая строка кода, комментарии могут отличаться --
AST их не видит) в обоих местах.
