# Находка: двойной клик может запустить разделение на партии дважды

Дата: 2026-09-30. Не исправлено в этом прогоне -- см. "почему не чиню
прямо здесь".

## Симптом

`POST /api/job/{id}/separate` (`web/app.py:api_separate_later`) проверяет
`job.status == "running"` по снимку `job`, снятому ДО списания денег и ДО
постановки в очередь:

```python
job = storage.job(job_id)
if job.status == "running":
    raise HTTPException(409, "Этот трек сейчас обрабатывается")
...
_charge_song_once(user, job)
runner.submit_separation(job_id)
```

А `status="running"` выставляется только внутри `_separate_later`
(`web/jobs.py`), когда поток из пула реально начал работу -- то есть
ПОСЛЕ постановки в очередь, а не в момент запроса.

## Почему это race

Деньги списываются верно: `_charge_song_once` -> `claim_job_charge`
атомарен (`UPDATE jobs SET counted = 1 WHERE id = ? AND counted = 0`), и
при гонке списывает только один из двух одновременных запросов. Но
проигравший запрос в гонке за списание НЕ получает ошибку -- функция
`_charge_song_once` просто молча возвращается (это специально: так и
должно работать для законного случая "трек уже оплачен, разделяем
бесплатно"). После этого `api_separate_later` всё равно безусловно
вызывает `runner.submit_separation(job_id)`.

Итог: два запроса (двойной клик, повтор из-за таймаута сети) почти
одновременно на один и тот же `job_id` -- оба проходят проверку статуса
(она читает СТАРЫЙ `status`, ещё не "running"), и оба ставятся в пул
потоков (`max_workers=2` по умолчанию). Оба потока пишут в одну и ту же
`out_dir/stems`, и `storage.update_job(job_id, result=...)` вызывается
дважды конкурентно -- какая запись выиграет, не определено. Денег это не
касается (списание останется однократным), но результат разбора на диске
может перемешаться или задвоить работу впустую.

## Предполагаемое направление фикса (не реализовано)

Нужен атомарный "захват на выполнение", аналогичный `claim_job_charge`,
но по статусу, а не по деньгам -- например
`storage.claim_job_run(job_id, allowed_from=("done",))`
(`UPDATE jobs SET status='running' WHERE id=? AND status IN (...)`,
вызывается в `api_separate_later`/`api_make_tabs` ДО `submit_separation`/
`submit_tabs`, а не внутри `_separate_later`/`_tabs`). Второй запрос,
проигравший эту гонку, должен получать 409, а не тихо проходить дальше.

Не реализовано в этом прогоне, потому что тот же примитив нужен
одновременно трём путям (`_separate_later`, `_tabs`, и внутренний вызов
`_separate_later` из `_lyrics`, который не должен блокироваться чужим
"running"), и без отдельного набора тестов на все три легко сломать
рабочий путь (например, сделать `_lyrics` неспособной дождаться уже идущего
разделения). Это тянет на отдельный, сфокусированный прогон с тестами
именно на эту гонку -- по той же причине, по которой находка в
`docs/findings-chord-quality.md` не чинится с наскока.
