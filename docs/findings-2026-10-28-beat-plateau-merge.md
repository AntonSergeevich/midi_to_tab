# Находка 2026-10-28: соседние кадры одной доли иногда считались двумя

Дата: 2026-10-28. Автономный прогон по мандату из CLAUDE.md. Продолжение
направления из находок 10-26/10-27 («основной блокер — качество
распознавания — по-прежнему в `audiochords.py`/`chordnet.py`», расширено
до соседнего `beatnet.py`, от которого зависит сетка тактов для тех же
аккордов).

## Симптом

`beatnet.py::_peaks()` склеивает соседние кадры одного пика в одну долю
(докстрока: «соседние кадры — одна доля»). Склейка работала верно только
для плато из ДВУХ кадров подряд; плато из трёх и более кадров с одинаковым
максимумом (`maximum_filter1d`, окно 7) рвалось на две доли вместо одной.

Числом (значения из `_peaks`, `FPS=50`):

| ширина плато (кадров) | было (долей) | стало (долей) |
|---|---|---|
| 2 | 1 | 1 |
| 3 | **2** (0.21, 0.24) | 1 |
| 4 | **2** (0.21, 0.25) | 1 |
| 6 | **3** (0.21, 0.25, 0.29) | 1 |

## Причина

Условие склейки `frame - merged[-1] <= 1` сравнивало очередной кадр плато
не с последним кадром, вошедшим в группу, а со скользящей СЕРЕДИНОЙ уже
слитой группы (`merged[-1]` — бегущее среднее). Середина при росте группы
отстаёт от последнего кадра: после кадров `[10, 11]` середина — `10.5`, и
третий кадр плато `12` даёт разрыв `12 - 10.5 = 1.5 > 1` — склейка
обрывается, хотя кадр `12` по-прежнему непосредственно соседствует с `11`.

Докстрока файла сама называет модель int8-квантованной — это делает
равные (тем самым широкие) плато логитов более вероятными, чем у модели
с полной точностью, то есть не редкий краевой случай, а ровно то
условие, которое квантование создаёт чаще.

## Почему это important: сетка тактов, не только доли

`beatnet.track()` используется и для чистых долей
(`midi2tab/audiochords.py:437`, через `beatgrid.py`), и как основа BPM
(`np.median(np.diff(beats))`) и тактов (`bars()` → привязка сильных
долей). Лишняя доля из разорванного плато двигает медиану интервалов и
может сдвинуть голосование по метру/фазе такта в `bars()` — то есть
ошибка на уровне «доли» долетает до сетки тактов, по которой выравниваются
аккорды на виде партитуры и табов.

## Фикс

`_peaks()` теперь хранит последний кадр плато отдельно от бегущей
середины и сравнивает очередной кадр именно с ним:

```python
last_frame = None
for frame in frames:
    if merged and frame - last_frame <= 1:
        count += 1
        merged[-1] += (frame - merged[-1]) / count
    else:
        merged.append(float(frame)); count = 1
    last_frame = frame
```

Середина (`merged[-1]`) остаётся как была — она идёт в итоговое время
доли (центр плато), просто больше не участвует в решении «склеивать или
нет». Поведение для уже верных случаев (одиночные пики, плато из двух
кадров, разнесённые пики) не меняется — проверено отдельно (см. тест).

## Тест

`tests/test_beatnet.py::test_peaks_merges_a_tied_plateau_of_any_width_into_one_beat`
(параметризован шириной плато 2/3/4/6) и
`test_peaks_still_separates_genuinely_different_beats` (две явно разные
доли не склеиваются). Проверено, что тест ловит именно починенный
симптом: временный `git stash` только `midi2tab/beatnet.py` — падает
ровно на плато шириной 3/4/6 (ширина 2 остаётся зелёной, как и было),
откат не коммитился. Полный прогон: 419 тестов (было 414) + 2
пропущенных, зелёный.

## Что проверял, но не стал трогать

- Реального влияния на числа с живого аудио не измерял — в песочнице
  агента нет доступа к размеченным записям с нужными характеристиками
  (нужна именно модель Beat This на реальном звуке, GuitarSet для этого
  не подходит — там нет своей разметки долей/такта для сверки). Фикс
  чисто логический: поведение описано докстрокой, но не соответствовало
  ей при плато шире двух кадров — это не гипотеза, требующая калибровки
  на размеченных песнях (как в `findings-chord-quality.md`), а
  несоответствие коду собственной спецификации, безопасное для любого
  входа (не может сделать склейку хуже, чем она уже работала для плато
  из ≤2 кадров).
- Конкурентный анализ не обновлял — последняя сверка 26.10, всего два дня
  назад; по мандату («не каждый раз») разумно пропустить этот прогон.
