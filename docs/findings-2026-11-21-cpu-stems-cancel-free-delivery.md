## Находка и фикс: `_stems_on_cpu` отдаёт результат бесплатно после отмены

CPU-разделение (`web/studio.py::StudioRunner._stems_on_cpu`, добавлено
19.11 коммитом `6403541` как запасной путь «Партий», когда видеокарта
RunPod недоступна — а она прямо сейчас недоступна уже день+ из-за
блокировки Cloudflare, см. находки 19.11/20.11) проверяет отмену
(`_cancelled`) только один раз — сразу после `separate.separate()`.
Дальше идёт кодирование в mp3 по каждой партии (`subprocess.run(ffmpeg)`,
до 900 с на вызов, несколько вызовов подряд для 6 партий) — отмену в
этом окне никто не перепроверяет, и функция безусловно вызывает
`self._finish(...)` с готовыми файлами после кодирования.

Кнопка "Остановить" (`/api/studio/{id}/cancel` -> `StudioRunner.cancel()`)
разрешена для любой задачи со статусом `running` — то есть ровно в это
время, пока кодирование идёт. `cancel()` немедленно помечает задачу
отменённой и возвращает деньги (`_fail()` -> `claim_studio_refund()`,
атомарно, снимает отметку "списано"). Но если в этот момент фоновый
поток `_stems_on_cpu` уже прошёл свою единственную проверку и дошёл до
кодирования, он доведёт его до конца и перезапишет job обратно в
`status="done"` с рабочими файлами — пользователь получает результат,
за который деньги уже вернули на баланс.

Окно для реального нажатия кнопки не микроскопическое: кодирование
шести партий в mp3 (`for name, path in sorted(parts.items())`) занимает
реальные секунды-минуты на процессоре сервера, и это именно тот момент,
когда нетерпеливый пользователь с наибольшей вероятностью жмёт
"Остановить" — задача уже идёт не первую минуту.

Обычный путь через RunPod (`_run`, строка ~1591) от того же класса
гонки защищён иначе: там `self._finish(...)` вызывается сразу после
единственного быстрого запроса статуса в цикле, который сам проверяет
`_cancelled()` на каждой итерации прямо перед этим — окно там на три
порядка короче (один HTTP-запрос, а не до 900 с ffmpeg × 6).

### Воспроизведено тестом

`tests/test_studio.py::test_cpu_stems_cancel_during_encoding_does_not_still_deliver`:
фальшивый `subprocess.run` для первого же ffmpeg-вызова (кодирование
первой партии) сам нажимает "Остановить" (`runner.cancel(job_id)`), как
если бы это сделал человек в браузере, потом как обычно пишет mp3.
На непропатченном коде: `job.status == "done"`, файлы в `job.result`
доступны (баланс при этом уже возвращён) — ровно бесплатная отдача.
Откатил фикс (`git stash`) — тест падает именно на этом; с фиксом — проходит.

### Фикс

`web/studio.py::_stems_on_cpu`: перед вызовом `self._finish(...)` —
ещё одна проверка `self._cancelled(job_id)`; если да — выйти без
перезаписи (деньги и статус остаются такими, какими их оставил
`cancel()`). Незавершённые mp3-файлы остаются в папке задачи (их не
отдаёт ни один API — все точки выдачи файлов проверяют `job.result`,
а он в этом случае не записывается) и будут убраны обычной уборкой
диска (`nasluh-cleanup`, см. `deploy/README.md`) как любые другие файлы
отменённой/старой задачи.

Полный `pytest` после фикса: 505 passed, 0 skipped, без регрессий.
