## `web/studio.py: StudioRunner._fail` -- не атомарный возврат денег

```python
def _fail(self, job_id: str, reason: str) -> None:
    job = self.storage.job(job_id)
    ...
    if job.counted and by_pack:
        self.storage.add_studio_credits(job.user_id, by_pack)
        self.storage.update_job(job_id, counted=False)
    elif job.counted and charged:
        self.storage.add_balance(job.user_id, charged)
        self.storage.update_job(job_id, counted=False)
```

Это чтение-потом-запись `job.counted` -- та же форма, что у уже
исправленного двойного возврата денег в `web/jobs.py`/`web/app.py`
(исправлено через `storage.claim_job_refund`: атомарный `UPDATE jobs
SET charged_kind = NULL WHERE charged_kind = ?`). Каждое другое место
возврата денег в кодовой базе уже переведено на `claim_job_refund` --
это единственное, что осталось на старой, не атомарной форме.

Почему не чиним прямо сейчас: `claim_job_refund` работает с полем
`charged_kind` (строка), а `_fail` читает/пишет `counted` (булево) --
это разные поля разной семантики (Студия списывает по-другому, чем
основной сайт: `_studio_charge_and_submit` сам атомарен при списании
через `spend_studio_credit`/`spend_balance`, и `counted=True`
выставляется уже ПОСЛЕ успешного атомарного списания, а не как
отдельный "застолбить" шаг). Проверены все вызывающие `_fail` места и
все пути, которыми `StudioRunner` отдаёт задачи пулу потоков
(`submit()`, `resume()`) -- воспроизводимого сегодня пути, где `_fail`
вызывается дважды конкурентно для одного и того же `job_id`, не нашлось:
у каждого действия Студии свой `uuid4` id, отдельной кнопки
"отменить"/повторной отправки в `_fail` для живой задачи нет, а
`resume()` выполняется один раз при старте (рестарт -- это
стоп-потом-старт, не два живых процесса одновременно). Добавлять новый
атомарный примитив специально под `counted` ради сценария, который
сегодня не воспроизводится, и без возможности написать на него
настоящий регрессионный тест (как `test_charge_song_once_survives_a_
true_concurrent_race` для уже исправленного случая) -- именно то
"не чинить вслепую то, что нельзя проверить", о чём просит текущий
мандат.

Направление на будущее: если когда-нибудь появится отдельная кнопка
"отменить" для живой задачи Студии (или любой другой способ дважды
вызвать `_fail` для одного job_id конкурентно), перевести `_fail` на
тот же атомарный приём -- например, `claim_job_refund`-подобный
`UPDATE jobs SET counted = 0 WHERE id = ? AND counted = 1` перед
возвратом денег, как уже сделано везде на основном сайте.
