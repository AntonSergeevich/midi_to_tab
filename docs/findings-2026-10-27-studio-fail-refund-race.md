# Находка 2026-10-27: сбой генерации Студии мог вернуть деньги дважды после рестарта

Дата: 2026-10-27. Автономный прогон по мандату из CLAUDE.md.

## Симптом

`StudioRunner._fail()` (`web/studio.py`) — единственное место, которое
возвращает деньги или генерацию из пакета за неудавшуюся Студию
(переделку, разделение, продолжение песни, клон голоса) — читало
`job.counted` в Python и затем писало `counted = False` ОТДЕЛЬНЫМ
запросом, уже после самого возврата (`add_balance`/`add_studio_credits`):

```python
if job.counted and by_pack:
    self.storage.add_studio_credits(job.user_id, by_pack)
    self.storage.update_job(job_id, counted=False)
    ...
```

Это ровно тот же порядок «прочитать снимок, потом написать», из-за
которого `grant_subscription` терял один из двух одновременных грантов
(находка 10-25) — только здесь опасное окно не между двумя запросами
от разных людей, а между падением процесса и повторным подхватом той
же задачи после рестарта.

## Причина

Автодеплой перезапускает `nasluh.service` на каждый пуш
(`deploy/update.sh`) — и сам этот файл уже один раз испугался похожего
окна чуть выше (`_run`: «рестарт застал задачу ровно между запросом к
видеокарте и записью её ответа»). Для `_fail` симметричное окно не
было закрыто: если процесс падает ПОСЛЕ `add_balance`/
`add_studio_credits`, но ДО `update_job(..., counted=False)` (и до
финальной записи `status="error"`, она идёт последней), на диске
остаётся задача со статусом `"running"`/`"queued"` и `counted` всё ещё
`True`. `resume()` после перезапуска подхватывает такую задачу
(`unfinished_studio_jobs()` ищет именно эти статусы) и гонит её через
`_run` заново; при повторном сбое `_fail` снова видит `counted = True`
и возвращает деньги или генерацию ЕЩЁ раз — тот же паттерн, что чинили
в `grant_subscription`, `claim_job_charge`, `claim_job_refund`,
`spend_balance` и остальных денежных функциях, но сюда дошла только
переделка слэш-аккордов 10-26, а не эта.

## Фикс

`web/storage.py::claim_studio_refund(job_id)` — атомарно снимает
отметку `counted` одним `UPDATE jobs SET counted = 0 WHERE id = ? AND
counted = 1`, как `claim_job_charge`/`claim_job_refund`. `_fail` теперь
сперва пробует застолбить право на возврат, и только если получилось —
решает, пакет это или баланс, и возвращает именно его:

```python
if self.storage.claim_studio_refund(job_id):
    if by_pack:
        self.storage.add_studio_credits(job.user_id, by_pack)
        ...
    elif charged:
        self.storage.add_balance(job.user_id, charged)
        ...
```

## Тест

`tests/test_studio.py::test_concurrent_fail_refunds_once_not_twice` —
два потока зовут `_fail` на одной задаче почти одновременно; чтобы
гонка реально проявилась (а не просто один поток не успел начать, пока
второй уже всё отработал), оба синхронизируются сразу после своего
первого чтения задачи (`storage.job`, через monkeypatch с
`threading.Barrier`) — тем же приёмом, которым размечена гонка в
находке 10-25. Проверено, что тест ловит регресс: временный откат
`studio.py`/`storage.py` на старый код (`git stash`) — тест падает,
баланс возвращается дважды (199 ₽ вместо 100 ₽), как и ожидалось.
Полный прогон — зелёный (410/410, было 409 до этого пункта и пункта
про свод по всем пользователям).
