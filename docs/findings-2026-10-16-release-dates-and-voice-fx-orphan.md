# Находка 2026-10-16: даты релизов «из будущего» и осиротевший файл в FX голоса

Дата: 2026-10-16. Автономный прогон по мандату из `CLAUDE.md`.

## Исправлено: три релиза в «Что нового» были датированы на день позже, чем выпущены

`web/releases.py` — версии 1.5, 1.6 и 1.7 (монтаж дорожек, запись голоса,
сведение одной кнопкой) хранили `date=dt.date(2026, 10, 16)`, хотя
`git log` по этим коммитам (`4e331cc`…`3d1254d`) показывает, что все они
были закоммичены и ушли в прод 2026-10-15 (с 02:12 до 10:47 UTC). Для
сравнения, версия 1.4 (коммит `11fece6`, тоже 2026-10-15) датирована
верно — 2026-10-15.

Это пользователю видно напрямую: окно «Что нового» и страница `/updates`
показывали дату релиза на день позже фактического дня, когда фича уже
стала доступна (то есть в момент самого первого показа окна релиз был
«из будущего» относительно даты на экране человека). Небольшая, но
настоящая и легко проверяемая по `git log -- web/releases.py`
неточность — поправил даты трёх версий на 2026-10-15. Логику
`unseen()`/`notice()` это не задевает (сортировка идёт по номеру версии,
не по дате), тесты не привязаны к конкретным датам.

## Исправлено: `/api/studio/{id}/voice` — файл обработки мог остаться осиротевшим на диске

`web/app.py: api_studio_voice` (нейросеть для своей дорожки — шумодав,
подтяжка нот) читала запись дорожки (`entry`) один раз в начале запроса,
затем секунды обрабатывала аудио (`_voice_slot`, ffmpeg/DeepFilterNet) —
**вне** замка `studio_runner._analysis_lock`, и только потом под замком
писала результат в `result["extras"]`, находя нужную запись по имени
файла из исходного запроса (`file`).

Если за эти секунды обработки дорожку с этим именем удалили
(`DELETE /api/studio/{id}/extra/{name}`), либо тот же файл параллельно
обработал второй запрос `voice` (меняющий его имя первым), запись под
замком находила ноль совпадений — `result["extras"] = [fresh_entry if
x["name"]==file else x ...]` просто оставляла список как есть, без
ошибки. Итог: только что созданный mp3 (`extra_<hex>.mp3`, результат
шумодава/подтяжки) оставался на диске, ни на что не ссылаясь — не
удаляется нигде, кроме истечения срока хранения всего трека. Деньгами
это не рискует (бесплатная функция), но тот же класс TOCTOU-гонки, что
уже чинился для квоты дорожек (`findings-2026-10-15`), просто на другом,
более новом участке кода.

Фикс: под тем же замком, перед записью, сверяем по свежим данным, что
дорожка с этим именем всё ещё существует; если нет — удаляем только что
созданный файл (для `undo` создания нового файла не было, фикс это
учитывает) и отвечаем `409` вместо того, чтобы молча потерять результат
и оставить файл на диске.

Регрессионный тест
(`tests/test_studio.py:
test_voice_endpoint_does_not_orphan_file_when_track_vanishes_mid_processing`)
подменяет `storage.job` так, что к моменту записи под замком дорожка уже
«исчезла» — проверен на коде до фикса (падает: файл остаётся на диске) и
после (проходит, файл убран, запись не тронута, ответ 409).

## Источник находок

Вторую находку (гонка в `api_studio_voice`) нашёл параллельный фоновый
агент-разведчик по целевому поиску в файлах, не покрытых прошлыми
findings (ему же — чистый отчёт о `web/billing.py`: гонок/расхождений
сумм там не нашёл). Первую (даты релизов) и фикс обеих — проверил и
применил сам.
