## Находка и фикс: возврат денег мог пропасть при входе в аккаунт

`storage.merge_wallet(from_user, to_user)` — перенос баланса/кредитов/
Студийных кредитов/подписки с анонимной записи на учётную при входе в уже
существующий аккаунт (`web/app.py:893,961`), рядом с `move_jobs`.

До фикса функция читала донора ОТДЕЛЬНЫМ подключением, ДО своей
транзакции (`donor = self.user(from_user)`), и только потом — уже в другой
транзакции — прибавляла снятый снимок к `to_user` и безусловно обнуляла
`from_user` (`balance=0, credits=0, studio_credits=0, paid_until=NULL`).

Между этими двумя шагами есть окно. Сценарий: анонимный посетитель платит
за трек (списание с баланса), трек ещё разбирается в фоне, и в этот момент
посетитель входит в уже существующий аккаунт. Если разбор проваливается и
`JobRunner`/`billing` возвращают деньги на анонимную запись (в фоновом
потоке) ровно в это окно — возврат не попадает ни в перенесённую сумму
(снимок уже снят до возврата), ни на донора (его обнуляют поверх). Деньги
пропадают бесследно: не у `to_user`, не у `from_user`. Ровно тот класс
"тихого" денежного бага, который проект уже чинил для подписки
(`grant_subscription_days`, через `UPDATE ... RETURNING` вместо
читать-в-Python-потом-писать) — `merge_wallet` был единственным местом, где
этот паттерн пропустили (отмечено в `findings-2026-10-12-keep-vocals-
price-and-cookie.md`, но про другую, продуктовую проблему той же функции —
про эту гонку там речи не было).

Воспроизвёл численно (вручную, до фикса, 20 повторов с потоками через
`threading.Barrier`: один поток — `merge_wallet`, другой — конкурентный
`add_balance` на донора): сумма `account.balance + visitor.balance` после
обоих потоков не совпадала с ожидаемой почти при каждом повторе.

Фикс — перенос и обнуление донора теперь в одном UPDATE с подзапросами к
его же строке (без отдельного чтения в Python до транзакции), внутри
одного `with self._connect()` — как `grant_subscription_days`. Подзапросы
читают текущий баланс/кредиты/подписку/тариф донора в момент самого
UPDATE, SQLite сериализует конкурентный `add_balance` на ту же строку
целиком до или целиком после этой транзакции (файловая блокировка на
запись) — потерять часть суммы АТОМАРНО невозможно: возврат либо попадёт
в перенос (уедет вместе с остальным), либо останется на доноре до
следующего входа, но нигде не пропадёт. `paid_until`/`tier` логика
(максимум остатков подписки, Студия не отнимается у Студии) перенесена в
SQL `CASE` без изменения смысла — обе старые регрессии (`test_merge_
wallet_moves_balance_credits_and_subscription`, `test_merge_wallet_keeps_
the_later_subscription`) проходят без изменений.

Новый тест `test_merge_wallet_survives_a_refund_landing_during_the_merge`
(`tests/test_auth.py`) — настоящие потоки через `threading.Barrier(2)`,
20 повторов, каждый раз проверяет сумму на обоих счетах после гонки.
Откатил только `web/storage.py` к версии до фикса — тест упал (100.0 вместо
137.0, то есть сам возврат на 37 потерялся) на первом же повторе; с фиксом
проходит стабильно. Полный `pytest`: 489 passed (было 488), без регрессий.

Запушено в рабочую ветку.

  блокировано отсутствием GPU и калибровочного набора.
