# Прогон 19.11.2026 (утро): реальный инцидент на проде

## Контекст

Начало дня — несколько прямых сообщений владельца о живых проблемах на
проде (не находки агента, а то, что он сам увидел): после переноса сервера
и восстановления бэкапа подряд обнаружились три эффекта. Этот файл —
задокументированная сводка той части прогона (коммиты `13dae63`..`ab4c1d0`,
сессия `session_01C8Xefyh91dYaiy4r5UAY9K`), у которой не было итоговой
записки — её и дописываю сейчас, в начале следующего прогона, прежде чем
продолжать.

## Три фикса, уже запушенные и живые на проде

1. **`deploy/backup_probe.py` + `restore_data.sh`** — бэкап Beget (19 ГБ)
   не влезал на диск (свободно ~8 ГБ) при обычной распаковке. Теперь размер
   папки данных читается из заголовков архива БЕЗ распаковки (`tarfile`/
   `zipfile`, `seek` по содержимому), план сравнивает его со свободным
   местом, объединение переносит распакованное `mv` (не копией), модели и
   треки нового сервера подключаются жёсткими ссылками — не занимают место
   второй раз.

2. **`web/studio.py::runpod_key_check()`** — после переноса RunPod начал
   отвечать на проверку страницей Cloudflare «Attention Required» (403), а
   проверка сайта интерпретировала любую ошибку как «ключ не подходит» —
   ложная тревога про несуществующую проблему с ключом. Теперь текст
   Cloudflare-блока даёт «не проверен», а не «не подходит»; настоящий 401
   (ключ действительно не тот) — всё ещё «не подходит». Тест
   `test_runpod_key_check_does_not_blame_the_key_for_cloudflare`.

3. **Разделение на партии — запасной путь на CPU сервера.** Та же
   Cloudflare-блокировка RunPod means видеокарта стала недоступна для
   реальной работы, не только для проверки ключа, а Suno (через GenAPI) не
   умеет делить ЗАГРУЖЕННЫЙ трек на партии (`task_id`/`audio_id` — только
   для треков, созданных самим Suno; проверено пробой
   `scripts/genapi_probes/stems_upload.json` — ответ «обязательны», когда
   их взять не у кого). Теперь при недоступной видеокарте (ошибка запуска
   на RunPod) или `NASLUX_CPU_STEMS=always` сервер делит трек сам, своим
   Demucs на процессоре, теми же моделями, что у воркера (`htdemucs_6s` —
   шесть партий, `htdemucs` — минус/голос), по одному треку за раз.
   `NASLUX_CPU_STEMS=0` выключает запасной путь вовсе. Тест
   `test_stems_fall_back_to_server_cpu_when_runpod_is_blocked`.

4. **Крутилки стиля при создании/переделке на Suno (GenAPI) — починка
   находки 13.11.** После переезда (нет ключа Mureka) YuE2 выключен, песни
   идут через GenAPI/Suno, а весь блок крутилок прятался — «пропали
   крутилки по стилю» (прямая жалоба владельца, не предположение). Вывод
   находки 13.11 («backend читает эти поля только при engine == runpod»)
   был верен только для «удержания мелодии»; влияние песни, силу стиля и
   странность `studio._hit_params` всегда передаёт Suno как `audio_weight`/
   `style_weight`/`weirdness`. Теперь видны: с нуля — сила стиля и
   странность; переделка — ещё влияние песни; «удержание мелодии» (нет
   смысла для Suno) скрыто. Живой тест в браузере + обновлённый
   `tests/test_studio_browser.py`, записка находки 13.11 дополнена
   поправкой.

Полный `pytest` на коммите `ab4c1d0` (голова ветки на старте этого
прогона): **488 passed, 5 skipped**, без регрессий. Эти пять коммитов уже
были на `origin/claude/epic-mccarthy-sl30hz` (запушены раньше, до старта
этого прогона) — проверено fast-forward'ом и `git fetch`, не перезапушено
повторно.

## Почему эта записка появилась только сейчас

Сессия, сделавшая эти пять коммитов, видимо кончилась (упёрлась в лимит
или была прервана) сразу после пуша последнего коммита, не оставив
итоговую записку прогона — такую, как у всех предыдущих дней
(`findings-2026-11-1[3-8]-*.md`). Код и тесты в порядке (проверено полным
прогоном pytest выше), содержательных пробелов в самой работе нет — только
в документации по заведённому для этого проекта формату. Дописываю её
сейчас, чтобы не терять след, что именно и почему было сделано, прежде чем
продолжать прогон дальше.
